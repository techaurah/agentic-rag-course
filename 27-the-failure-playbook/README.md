# Lesson 27: The failure playbook: classifying what breaks

**Time:** about 60 minutes · **Difficulty:** Intermediate · **Prerequisites:** Lessons 18 and 20 · **You need:** The shipped pipeline; this lesson interrogates it.

When a RAG system misbehaves in production, the first hour decides whether the incident becomes a fix or a folklore. This lesson builds the classification habit as a tool: run the pipeline over the golden set, sort every imperfection by the layer that caused it, and attach to each class its diagnosis path and its fix. The playbook below is generated by the artifact from the current system, so it can never drift out of date silently; rerun it after any change and the table is the change's incident forecast.

## The shipped system's table

Of 32 golden questions, 26 are fully clean (answered with every gold fact, or correctly refused). The other 6 are classified below, and none of them is a mystery: each has a layer, an owner, and a fix path. (q17 sat in this class until the offers archive was marked superseded in the manifest; with the stale sentence filtered, the composer now picks the current one. Corpus metadata fixed what composer tuning could not, which is why Lesson 25's discipline is part of this playbook.) The fix is Lesson 23's: multi-sentence composition or a generating model under the grounding checker. **False answer: q24.** The known price matching miss from Lesson 20, intent level, still open, documented as the system's named residual risk. **False refusal: none.** The refusal dial's current setting holds its side of the trade.

## How to run an incident with this playbook

Reproduce the user's question against the golden harness shape: check the pack (was the evidence there?), then the answer against the pack (grounded?), then the refusal tests (should it have answered at all?). The first layer where reality diverges from the class expectation is the layer that owns the bug. Two disciplines make this fast in practice: the pack is logged with every production answer (Lesson 14), so reproduction is reading, not archaeology; and every production failure that survives diagnosis becomes a golden set candidate (Lesson 19), so the playbook's table grows teeth with every incident. A failure class with no golden coverage is a promise to be surprised by the same bug twice.

## Run it

Run `python3 failure_playbook.py`. `evaluate()` returns the classified table and the fix path per class. Compare it against Lesson 20's scorecard: same system, two views (scores for gates, classes for work), and a healthy team keeps both.

## Common failures

- **Fixing the layer that is loudest.** A wrong answer feels like a model problem; the table shows most of this system's imperfections are composition shape and one is retrieval depth. Classify before fixing.
- **Playbooks written once, by hand.** They rot with the system. Generate the table from the harness, as here, and let prose explain a table that is always current.
- **Incidents that never become golden questions.** The set is the institutional memory. If a failure is not in it, the system has agreed to relearn it later at production prices.
